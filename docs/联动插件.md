# 联动插件：文件保存 → git 状态刷新

## 联动对象

[DSH-better-sidebar](https://github.com/mays-hi/DSH-better-sidebar)（对话侧栏插件）v0.27.0+ 的文件保存事件。内置编辑器保存文件成功后，它的宿主半 emit cordis 事件 `better-sidebar/file-saved`，payload 为 `{ sessionId, cwd, path, size?, mtimeMs?, at }`：`path` 是保存时的原样路径（可能是相对路径、两种分隔符都可能出现），`cwd` 是该会话解析出的工作区根。事件契约见该插件仓库的 `docs/file-save-events.md`。

## 触发链路

1. 读者在 DSH 内置编辑器里保存文件，请求打到 better-sidebar 的 `/sidebar/write` 路由；
2. 写入成功、应答写回之后，better-sidebar emit `better-sidebar/file-saved`；
3. 本插件宿主半的订阅（`src/host/79b-file-save.js`）收到事件：把 `path`（相对的与 `cwd` 字符串拼接）解析到所属仓库——候选集是配置登记 ∪ 会话工作区（79-live-watch.js 的 `liveRepoList`），带分隔符边界的最长前缀匹配；
4. 命中即失效宿主自己的读缓存（`invalidateRepo`，便宜操作不防抖），再按仓库挂 1.5 秒尾沿防抖；
5. 防抖到点且有浏览器连着时，广播 `repo-changed`；
6. 浏览器半的现成 handler（`src/client/98-register.js`）收到后 markTreePartial + ringTreeReload + bumpData，变更页与 chip 走 `⟳` 那条整树刷新。

连按 Ctrl+S 是一波：同一仓库 1.5 秒内的后续保存只把定时器往后推，停手后才广播一次。但每下保存都立刻失效宿主读缓存，防抖期间面板自己来读也拿到新答案。

## 各情形行为

| 情形 | 行为 |
|---|---|
| DSH-better-sidebar 未安装 | 没人 emit 这个事件，订阅在但 listener 永不触发。零报错，其余功能照旧 |
| 装了但 < 0.27.0 | 同上：旧版不 emit 这个事件。零报错；宿主升到 0.27.0+ 后自动开始生效，无需任何操作 |
| bridge 构建（dist/host.js，无 liveHub） | 订阅与读缓存失效照常工作；防抖到点的广播一步被 typeof 守卫安静跳过 |
| 保存路径不属于任何已知仓库 | 最长前缀匹配命不中，安静返回。不失效缓存、不广播 |
| 没有浏览器连接 | 读缓存照常失效；广播一步因 liveHub.sockets 为空跳过 |

五种情形都是 silent no-op。listener 全程 try/catch，绝不向保存路由抛错——已完成的保存不因订阅方沾上任何动静。

## 边界

- 只覆盖走 `/sidebar/write` 的保存：内置编辑器是它，走 `api.fsWrite` 的 viewer 也在这条路上。上传、rename、archive 等其他写路径不广播。
- 模型在会话里用工具改文件（write / edit）不走这个事件——那仍由 session-complete 推送与客户端 watcher 轮询两条现有通道覆盖，本联动不替代它们。
- 本联动也不替代 watcher 轮询：它只是多一条即时通知。轮询的节奏与「本来干净、刚刚被改」的可见时机，见 README「一次『仓库动过了』之后，插件要花多久才排空」一节。

## 为什么不做 client 半

client 面订阅 `ctx.betterSidebar.onFileSaved(...)` 必须声明 `inject: ['betterSidebar']`：better-sidebar 未安装时整个 git 插件会被 cordis 停等，chip 和面板一起消失——不可接受。自己探测 features 再加重试则复杂且收益为零：宿主广播毫秒级到达，且天然覆盖所有浏览器，不必每个浏览器各订一遍。宿主面对未安装、旧版本完全免疫，正是这个需求该用的暴露面。

## 手动验证

1. 确认 DSH-better-sidebar 已安装且 ≥ 0.27.0，浏览器连着，目标仓库在面板仓库列表里（或就是会话工作区本身）；
2. 打开 git 面板的「变更」页（或看着 chip 的改动数）；
3. 在 DSH 内置编辑器里改这个仓库里的一个文件并保存；
4. 约 1.5 秒内变更页刷新：原本干净的仓库里该文件出现在变更树，chip 的改动数跟着变。
